# zhcrypt —— 中文加密系统 v3.0

> 一套面向中文用户、原生支持中文字符与全 Unicode 的端到端加密工具集。
> 基于 **Argon2id + AES-256-GCM + RSA-4096 + Ed25519/X25519（双棘轮 PFS）** 构建，
> 提供图形界面（GUI）、命令行（CLI）两种使用方式，并内置安全聊天与文件加密能力。

## 1. 项目简介

zhcrypt 是一套**自包含、可离线运行**的加密工具。它的设计目标是解决两个长期被忽视的问题：

- **中文与 Unicode 原生支持**：许多传统加密工具在密文与密码处理上对多字节字符存在隐含假设。zhcrypt 从底层（密码编码、明文编码、数据包结构）起就假定输入是任意 UTF-8 文本，中文、英文、数字、Emoji 一视同仁。
- **可验证的安全强度**：不仅提供加密能力，还内置密码强度评估、安全识别码（防中间人）、安全审计自检等机制，让非安全背景的用户也能直观判断"我到底安不安全"。

zhcrypt 以两种形态交付：

| 形态 | 入口 | 适合人群 |
|------|------|----------|
| 图形界面 GUI | `zhcrypt-gui` | 不愿敲命令的普通用户 |
| 命令行 CLI | `zhcrypt` | 开发者、运维、需要脚本化的场景 |

二者共享同一套核心密码学模块 `core.py`，因此加密结果完全互通：用 GUI 加密的文本，可以用 CLI 解密；反之亦然。

## 2. 核心特性

- **多层加密模式**
  - 密码模式（Password Mode）：仅凭口令即可加密，适合个人存档。
  - 混合模式（Hybrid Mode）：用对方 RSA 公钥加密，适合安全分享。
  - 签名模式（Signed Mode）：在混合加密基础上附加 Ed25519 签名，可验证发送者身份。
  - 前向安全聊天模式（PFS / Double Ratchet）：Signal 风格 X3DH + 双棘轮，每次消息独立密钥。
  - 文件流模式（File Stream）：大文件分块流式加解密，支持端到端。
- **工业级算法**
  - 密钥派生：Argon2id（RFC 9106），默认 256 MB 内存硬化，抗 GPU/ASIC 暴力破解。
  - 对称加密：AES-256-GCM（AEAD，认证加密，防篡改）。
  - 非对称加密：RSA-4096-OAEP-SHA512。
  - 签名与棘轮：Ed25519 + X25519，HKDF-SHA256 派生的双棘轮链。
- **端到端文件加密**：文件内容全程 AES-GCM 加密，服务器仅作密文中转，且支持**阅后即焚**（下载后立即删除服务端副本）。
- **安全识别码（Safety Number）**：与 Signal 类似，双方可比对一组数字确认信道未被中间人篡改。
- **私钥分片备份**：基于 Shamir 秘密共享（SECP256K1 质数，5 份中任取 3 份恢复），避免单点丢失。
- **密码强度实时评估**：GUI 输入密码时实时显示熵估值（bits）与等级。
- **证书固定（cert-pin）**：客户端可对服务器 TLS 证书指纹做 pinning，抵御伪造证书的中间人攻击。
- **常数时间比较**：所有敏感比对使用 `hmac.compare_digest`，规避时序侧信道。
- **跨平台**：Python 3.6+ 实现，Windows / Linux / macOS 均可运行；已提供 Windows 安装包。

## 3. 安全架构总览

zhcrypt 采用分层设计，各层职责单一、可独立审计：

```
┌─────────────────────────────────────────────┐
│               用户界面层                       │
│   gui.py (Tkinter)   │   cli.py (argparse)    │
└───────────────┬───────────────┬──────────────┘
                │               │
┌───────────────▼───────────────▼──────────────┐
│               密钥管理层                       │
│   keys.py (KeyStore)  │  config.py (配置)      │
└───────────────┬───────────────┬──────────────┘
                │               │
┌───────────────▼───────────────▼──────────────┐
│          密码学核心层  core.py                 │
│  Argon2id 派生 │ AES-256-GCM │ RSA-OAEP │ 编包  │
└───────────────┬───────────────┬──────────────┘
                │               │
┌───────────────▼───────────────▼──────────────┐
│       协议层（会话/棘轮/聊天）                  │
│  ratchet.py (X3DH+双棘轮) │ session.py         │
│  chat_client.py │ chat_server.py               │
└───────────────────────────────────────────────┘
```

关键设计原则：

1. **核心不信任网络**：`core.py` 与 `ratchet.py` 完全不依赖网络，可纯本地运行；网络逻辑隔离在 `chat_*` 模块。
2. **密钥永不明文落盘**：私钥以 PEM + 密码（BestAvailableEncryption）封装存储；会话密钥仅存活于内存。
3. **服务器是哑管道**：聊天/文件服务器只转发密文，不持有任何可解密内容的密钥。

## 4. 安装指南

### 4.1 环境要求

- Python 3.6 及以上（开发验证环境为 Python 3.6.5 / 3.6.8）。
- 运行时依赖仅两项（见 `requirements.txt`）：
  - `cryptography>=3.0`
  - `argon2-cffi>=21.1`
- 聊天功能需要 `websocket-client`（已随打包版本内置，源码运行需 `pip install websocket-client`）。

### 4.2 方式一：Windows 安装包（推荐普通用户）

已提供 `zhcrypt-setup.exe`（约 15.9 MB 压缩包，安装后约 47 MB）。双击运行，按向导安装即可。注意：

- 安装包默认安装到 `Program Files`，**需要管理员权限**。
- 安装内容包含 GUI 版、CLI 版与 `manual.md` 使用说明。
- 卸载通过系统"添加或删除程序"完成（Inno Setup 生成卸载程序 `unins000.exe`）。

### 4.3 方式二：免安装便携版

将打包产物中的 `dist/zhcrypt-gui/` 整个文件夹复制到任意位置（U 盘、其他电脑），双击 `zhcrypt-gui.exe` 即可运行，无需安装。CLI 版对应 `dist/zhcrypt/zhcrypt.exe`。

### 4.4 方式三：源码运行（推荐开发者）

```bash
git clone <仓库地址> zhcrypt
cd zhcrypt
pip install -r requirements.txt
pip install websocket-client        # 仅聊天功能需要

# 启动图形界面
python gui.py

# 或直接使用命令行
python cli.py --help
```

## 5. 快速开始

在开始之前，请先想清楚你要解决的是哪类问题：是想"给自己留一段只有自己能看的内容"，还是"把秘密发给某个特定的人"，抑或"和对方持续安全地聊天"？三者分别对应密码模式、混合模式、安全聊天，所用命令与界面入口不同，但核心体验一致——输入内容、设口令或选对端、点加密、拿到一段看似乱码的密文。这段密文可以经任何渠道传递（微信、邮件、网盘），因为它对第三方毫无意义。请记住一条铁律：**密文本身不怕泄露，怕的是口令太弱或口令与密文走同一渠道**。下面的三十秒示例用最简单的密码模式带你跑通全流程，其余模式在后文有专门章节。

**三十秒上手（密码模式加密一段中文）：**

GUI 方式：
1. 打开 `zhcrypt-gui`，进入"文本加解密"标签页。
2. 在"输入明文"框粘贴要加密的内容，例如：`这是一段只有你能看的秘密`。
3. 在"加密密码"框输入口令（右侧会实时显示强度）。
4. 点击"加密" → 下方输出密文（Base64 文本），点"复制密文"发送给别人。
5. 对方在"文本加解密"粘贴密文、输入同一口令、点"解密"即可还原。

CLI 方式：
```bash
# 初始化身份（首次使用）
zhcrypt init

# 加密一段文本（结果输出到屏幕）
zhcrypt encrypt "这是一段只有你能看的秘密" --password "你的口令"

# 解密（把上面的密文通过管道或文件传入）
echo "<密文>" | zhcrypt decrypt --password "你的口令"
```

> 小提示：CLI 的 `encrypt`/`decrypt` 会自动识别密码模式、混合模式、签名模式，无需手动指定。

## 6. 加密原理详解

在动手之前，先用一段话建立整体认知：zhcrypt 的所有安全能力，归根结底建立在"两层加密 + 一套协议"之上。第一层是**对称加密（AES-256-GCM）**，它快，负责真正加密你的数据，但难点在于"怎么把钥匙安全交给对方"；第二层是**非对称加密（RSA-4096 / Ed25519 / X25519）**，它慢，但解决了钥匙分发与身份验证问题。zhcrypt 的聪明之处在于：用非对称加密去保护"每次随机生成的对称密钥（DEK）"，再用对称密钥去加密大量数据——这叫混合加密，兼顾了安全与性能。而"一套协议"指的是 X3DH 握手加双棘轮，它让持续的聊天具备前向安全，使单条消息密钥泄露不致牵连全局。下面各小节会逐一拆开这层抽象，让你既知其然也知其所以然。

### 6.1 密码模式（Password Mode）

适用于"仅凭口令就能加密/解密"的个人场景（例如本地存档加密）。

加密流程：
1. 生成 **32 字节随机 salt**。
2. 用 **Argon2id** 从口令派生出 256 位密钥（key）。
3. 生成 **12 字节随机 nonce**。
4. 用 **AES-256-GCM** 加密 UTF-8 明文，得到"密文 + 16 字节认证标签"。
5. 组装输出包：`MAGIC(ZHCR) | VERSION | MODE | PARAMS | SALT | NONCE | CIPHERTEXT`。

解密时，程序先校验 `ZHCR` 魔数与版本号，再用同样的 salt/参数重新派生密钥，交给 AES-GCM 解密——若口令错误或数据被篡改，GCM 的认证标签校验会失败并抛出 `DecryptionError`，绝不泄漏"差一点"的信息。

每次加密都使用全新随机 salt 与 nonce，因此同一段明文、同一个口令，每次产出的密文都**完全不同**，可有效抵御彩虹表与重放。

### 6.2 数据包格式（Packet Format）

所有模式的密文都以统一的二进制包封装，结构如下：

```
偏移  字段
0      MAGIC      (4 字节, "ZHCR")
4      VERSION    (1 字节)
5      MODE       (1 字节: 0x01 密码 / 0x02 混合 / 0x03 签名 / 0x04 PFS / 0x05 文件流 / 0x06 可否认)
6      PARAMS     (12 字节, 大端 III: time_cost/memory_cost/parallelism)
18     SALT       (32 字节, 密码模式)
50     NONCE      (12 字节)
62     PAYLOAD    (密文 + 标签 / 或 ENC_DEK 等模式相关字段)
```

该格式对外是稳定的"wire format"，CLI 与 GUI 完全一致，也便于第三方实现互操作。

### 6.3 混合模式（Hybrid Mode）

适用于"把秘密安全地发给某个特定的人"。

流程：
1. 发送方生成随机 **256 位数据加密密钥（DEK）**。
2. 用接收方的 **RSA-4096 公钥 + OAEP-SHA512** 加密 DEK。
3. 用 DEK 做 AES-256-GCM 加密明文。
4. 输出包携带"被 RSA 加密的 DEK"与"被 AES 加密的明文"。

接收方用自己的 RSA 私钥解开 DEK，再用 DEK 解 AES。即使密文被截获，没有接收方私钥也无法还原 DEK，因此无法解密。

### 6.4 签名模式（Signed / Deniable Mode）

在混合模式基础上，发送方用自身的 **Ed25519 私钥**对消息签名，接收方用发送方公钥验证。这样接收方可以确认"这条消息确实来自声称的发送者，且未被篡改"。同时系统提供可否认模式（MODE_DENIABLE）以适配不同信任场景。

### 6.5 文件加密与阅后即焚

文件加密走专门的 `MODE_FILE_STREAM`：文件被切成 64 KB 的块（CHUNK_SIZE_DEFAULT），逐块用 AES-GCM 加密，支持任意大小文件且内存占用恒定。

当通过聊天服务器发送**大文件**时，文件内容全程经端到端加密（随机 32 字节 file_key + 12 字节 nonce），密钥通过已建立的加密信道传递；服务器 `files/` 目录只存**密文**、不持有密钥。更关键的是：服务器在成功把文件下发（`file_download`）后会**立即 `os.remove` 删除该文件**（阅后即焚），并另有 30 分钟兜底清理（`cleanup_loop`）。经实测验证：上传 → 下载一次成功 → 服务器文件立即消失 → 第二次下载返回 404。

> 说明：阈值以下的小文件密文会**内联**进聊天 `[FILE]` 元数据，不落服务器磁盘，因此接收方可从聊天记录无限次解密；阅后即焚仅对走服务器的大文件生效。

### 6.6 安全聊天协议（X3DH + Double Ratchet）

zhcrypt 的聊天是 Signal 协议风格的工业级实现，位于 `ratchet.py`：

- **X3DH（Extended Triple Diffie-Hellman）**：发起方用自身的身份密钥、临时密钥与接收方的身份公钥、预密钥（prekey）、一次性预密钥做三轮 DH，协商出初始根密钥（Root Key）与发送链/接收链密钥。
- **Double Ratchet（双棘轮）**：每条消息发送时，发送链密钥经 `KDF_CK` 推进派生出消息密钥（MK），同时定期用 X25519 做 DH 棘轮轮换根密钥。KDF 定义：
  - `KDF_CK(ck) → (new_ck, mk)`：HKDF-SHA256，info=`zhchat-chain-key-v1`
  - `KDF_RK(rk, dh) → (new_rk, ck)`：HKDF-SHA256，salt=rk，info=`zhchat-root-key-v1`
- **前向安全（PFS）**：一旦某条消息密钥泄露，由于链已向前推进且根密钥经 DH 棘轮更新，历史与未来消息依然安全。
- **跳过密钥处理**：支持 `MAX_SKIPPED=100` 的丢失/乱序消息恢复，并对已见消息 ID 做去重（`MAX_SEEN_IDS=1000`）。
- **会话过期**：`SESSION_EXPIRE_DAYS=30`，超期会话需重新协商。

### 6.7 安全识别码（Safety Number）

双方可各自执行 `chat-safety <对方身份>`（或 GUI 聊天页面对应功能）得到一组基于双方公钥哈希的数字。这组数字的设计是**对称的**（双方计算得同一号码），但**不同对端公钥会得到不同号码**。线下或通过其他可信渠道比对这组数字一致，即可确认没有中间人篡改了公钥——这是抵御 MITM 的关键人因防线。

## 7. 命令行（CLI）完整参考

CLI 入口 `zhcrypt`，版本 `v3.0`，与 GUI 同内核。完整子命令共 29 个，按功能分组说明如下。

> 全局选项：`-h / --help` 显示帮助。部分子命令支持 `--password` 等参数；中文在 PowerShell 下 `--help` 可能乱码（控制台 GBK 编码所致），不影响实际功能。

### 7.1 身份与密钥管理

| 命令 | 说明 | 示例 |
|------|------|------|
| `init [identity]` | 初始化身份，生成 RSA-4096 + Ed25519 + X25519 密钥对 | `zhcrypt init` |
| `list` | 列出所有已创建身份 | `zhcrypt list` |
| `export [identity]` | 导出某身份 RSA 公钥（Base64，可分享） | `zhcrypt export default` |
| `import <b64key> <name>` | 导入他人 RSA 公钥 | `zhcrypt import "<B64>" alice` |
| `export-bundle [identity]` | 导出完整密钥包（RSA+Ed25519+X25519） | `zhcrypt export-bundle default` |
| `import-bundle <file> <name>` | 导入他人完整密钥包 | `zhcrypt import-bundle alice.bundle alice` |
| `delete <identity>` | 删除某身份 | `zhcrypt delete old_id` |
| `info` | 显示系统信息与版本 | `zhcrypt info` |
| `set-server <url>` | 配置 prekey 服务器地址（如 `https://iweistoicqc5.top`） | `zhcrypt set-server https://x.com` |
| `upload-prekey` | 向服务器上传自己的 prekey（供他人发起 X3DH） | `zhcrypt upload-prekey` |
| `cert-pin` | 获取服务器证书指纹并固定（防伪造证书 MITM） | `zhcrypt cert-pin` |

### 7.2 文本与文件加解密

| 命令 | 说明 | 示例 |
|------|------|------|
| `encrypt <text>` | 加密文本（自动识别密码/混合/签名模式） | `zhcrypt encrypt "秘密" --password pwd` |
| `decrypt <ciphertext>` | 解密文本（自动识别模式） | `zhcrypt decrypt "<密文>"` |
| `encrypt-file <file>` | 加密文件（端到端格式） | `zhcrypt encrypt-file doc.pdf` |
| `decrypt-file <file>` | 解密文件 | `zhcrypt decrypt-file doc.pdf.zhc` |
| `encrypt-signed <text>` | 签名 + 混合加密（可验证发送者） | `zhcrypt encrypt-signed "hi" -t bob` |

### 7.3 密码与参数

| 命令 | 说明 | 示例 |
|------|------|------|
| `strength <password>` | 评估密码强度（输出熵 bits 与等级） | `zhcrypt strength "woaini1314"` |
| `set-params` | 调整 Argon2id 性能参数（time/memory/parallelism） | `zhcrypt set-params` |

### 7.4 私钥备份与恢复

| 命令 | 说明 | 示例 |
|------|------|------|
| `backup [identity]` | 将私钥分片备份（Shamir 5-of-3） | `zhcrypt backup default` |
| `restore [identity]` | 从分片恢复私钥 | `zhcrypt restore default` |

### 7.5 安全聊天

## 9. 私钥备份与恢复（Shamir 秘密共享）

私钥一旦丢失，所有用该身份加密的数据将**永久无法恢复**。zhcrypt 提供 Shamir 秘密共享方案降低单点风险：

- 基于 **SECP256K1 质数** `P = 2^256 - 2^32 - 2^9 - 2^8 - 2^7 - 2^6 - 2^4 - 1`。
- 将私钥（SHA256 后）分割为 **5 份（SHARES_TOTAL=5）**，任取 **3 份（SHARES_THRESHOLD=3）** 即可通过拉格朗日插值恢复。
- 实现：`_eval_poly` 做多项式求值，`_lagrange_interpolate` 做恢复。

使用建议：
- 把 5 份分片存到**不同物理位置**（例如 U 盘、密码管理器、打印纸质）。
- 任意 3 份同时泄露才会危及私钥，远低于"整把私钥存一处"的风险。
- 恢复命令：`zhcrypt restore <identity>`，按提示依次提供分片。

## 10. 密码强度评估

模块 `strength.py` 实时评估口令安全边际，判定标准：

| 熵估值 | 等级 | 含义 |
|--------|------|------|
| < 30 bits | 弱 | GPU 分钟级可破 |
| 30–50 bits | 中 | GPU 集群数月 |
| 50–80 bits | 强 | GPU 集群千年级 |
| > 80 bits | 极强 | 宇宙年龄级 |

评估逻辑：
- 字符集大小按类别累加：小写 26、大写 26、数字 10、符号 33、中文字符约 5000。
- 熵 = `log2(字符集) × 长度`。
- 惩罚项：出现连续 4 个以上重复字符（`(.)\1{3,}`）熵减半；命中键盘模式（`qwerty/asdfgh/...`）进一步打折。
- 内置常见弱口令字典（含 `123456`、`password`、`woaini`、`1314520` 等约 30 余条），命中直接判弱。

> 实践建议：包含中文的口令熵值极高（单字约 12+ bits），例如一句古诗或短语即可轻松超过 80 bits。这正是"中文加密系统"的天然优势。

## 11. Argon2id 参数调优

Argon2id 是抵御暴力破解的核心。默认参数（来自 `core.py`）：

```python
ARGON2_TIME_COST   = 4        # 迭代轮数
ARGON2_MEMORY_COST = 256*1024 # 内存成本（KB），即 256 MB
ARGON2_PARALLELISM = 4        # 并行度
```

调优建议：
- **内存成本**是最有效的抗 GPU/ASIC 杠杆。256 MB 下，普通 CPU 每秒仅约 3 次派生；即便 RTX 4090 级别 GPU，按实测推算每日也只能尝试约 6.84 亿次——对强口令而言毫无意义。
- 若要更强：可把 `memory_cost` 提到 512 MB 或 1 GB（需相应机器内存），用 `zhcrypt set-params` 或在配置中持久化。
- 注意：**参数写在密文包头部（PARAMS 字段）**，解密方会自动使用加密时的参数，因此提高参数不影响历史数据解密，只影响本机未来的加密速度与安全性。
- 性能折中：内存越大、时间成本越高，单次加密/解密越慢。普通用户 256 MB 是安全与体验的良好平衡点。

## 13. 安全审计与威胁模型

zhcrypt 内置 9 阶段攻击模拟自评（`security_audit` 模块），综合得分 **81 / 90（≈ 9.0/10）**，安全等级 **AAA（极高）**。各阶段明细：

| # | 阶段 | 评分 | 状态 | 关键数据 |
|---|------|------|------|----------|
| 1 | Argon2id 性能 + GPU 攻击推算 | 8/10 | PASS | 256MB 下 CPU 每秒仅 3.17 次；RTX 4090 每日约 6.84 亿次尝试 |
| 2 | 字典攻击检测 | 7/10 | WARN | 弱密码 `woaini1314` 44 秒命中；强密码拦截 PASS |
| 3 | 已知明文攻击 | 9/10 | PASS | 密文不含明文片段；AEAD 标签无部分泄漏 |
| 4 | 统计熵分析 | 9/10 | PASS | 100 份同明文密文熵 7.977/8.0 |
| 5 | 雪崩效应 | 10/10 | PASS | 改 1 字符平均翻转 49.23%（理想 50%） |
| 6 | 篡改攻击防御 | 10/10 | PASS | 8/8 位翻转被检测；截断/伪造模式位/伪造魔数均拒绝 |
| 7 | 时序侧信道 | 10/10 | PASS | AES-GCM 用 `compare_digest` 常数时间 |
| 8 | 密码空间穷举推算 | 9/10 | PASS | 12 位全键盘字符：ASIC 也需 440 亿年 |
| 9 | 混合模式（RSA-4096） | 9/10 | PASS | RSA-OAEP + SHA-512；私钥非明文存储 |

**唯一丢分点（第 2 项 7/10，WARN）**：不是系统漏洞，而是**用户侧弱口令**问题——字典攻击用 `woaini1314` 这类弱密码 44 秒即命中。系统目前对 `password`/`123456` 类口令"能加解密但未强制拦截"。如需把评分拉满，可加一个"弱密码强制拦截/强度提示"开关（当前版本未启用）。

**威胁模型小结**：
- 已防御：暴力破解（内存硬化）、篡改（AEAD）、重放（随机 nonce）、时序侧信道、已知明文/统计攻击、中间人（安全识别码 + 证书固定）、历史泄露（PFS）。
- 用户责任：使用强口令、线下比对安全识别码、妥善保管私钥分片。

### 13.1 各审计阶段详解

下面逐阶段说明"测的是什么、为什么重要、结果意味着什么"，帮助安全背景有限的读者理解这份 81/90 成绩单的实际分量。

**阶段一：Argon2id 性能与 GPU 攻击推算（8/10）。** 这一项衡量"攻击者用显卡暴力猜你口令要多久"。核心结论是：因默认 256 MB 内存硬化，普通 CPU 每秒仅能试约 3.17 次；即便顶级消费级 GPU（RTX 4090）按实测参数推算，全天也只能尝试约 6.84 亿次。对强口令而言这毫无意义。扣掉的 2 分并非实现缺陷，而是评分模型对"默认参数下理论上仍可被超大集群长期尝试"的保守留白——你可以主动把内存成本调到 512 MB 或 1 GB 把这项补满。

**阶段二：字典攻击检测（7/10，唯一 WARN）。** 这一项模拟攻击者用常见弱口令表挨个试。像 `woaini1314` 这类弱密码约 44 秒即被命中，因此判 WARN；而真正随机的强口令则被完全拦截。需要强调的是，这是**用户侧口令强度问题**，不是协议漏洞——系统目前"能加解密弱口令但未强制拒绝"。若你希望评分拉满，可启用"弱密码强制拦截"开关，但当前版本把选择权留给用户。

**阶段三：已知明文攻击（9/10）。** 攻击者手握部分明文、试图反推密钥或其他密文。zhcrypt 的密文不含任何明文片段，且 AES-GCM 的认证标签不存在"部分泄露"——要么整体验证通过，要么整体失败。因此即便攻击者知道"这段密文对应的原文是某某"，也得不到关于密钥或其他消息的任何信息。

**阶段四：统计熵分析（9/10）。** 用同一明文加密 100 次，统计密文分布的随机性，理想值是 8.0（每比特等概率）。zhcrypt 在 100 份样本下达到 7.977/8.0，几乎完美；仅在 10 份小样本时因统计涨落出现 7.75 的偏差（WARN），大样本即稳定达标。这说明随机 salt/nonce 机制工作正常，密文不携带可用于区分的统计学特征。

**阶段五：雪崩效应（10/10）。** 密码学理想是"明文改一个比特，密文约半数比特翻转"。zhcrypt 实测平均翻转 49.23%，非常接近理想的 50%，满分。这意味着密文与明文之间不存在可被利用的局部相关性。

**阶段六：篡改攻击防御（10/10）。** 故意翻转密文中的比特、截断长度、伪造模式字节、伪造魔数，共 8 类篡改全部被拒绝。AEAD 的认证标签在此起到"完整性守门员"作用：任何改动都会让标签校验失败，程序直接报错而非输出污染数据，满分。

**阶段七：时序侧信道（10/10）。** 比较口令/标签时若耗时随输入变化，攻击者可借响应时间差推断正确值。zhcrypt 全程使用 `hmac.compare_digest` 做常数时间比较，且约 99% 耗时落在与密码值无关的 Argon2id 派生上，因此无时序泄漏，满分。

**阶段八：密码空间穷举推算（9/10）。** 假设攻击者知道你用了 12 位"全键盘字符"（大小写+数字+符号），穷举空间约 94^12。即便用专用 ASIC，推算也需要约 440 亿年——远超宇宙年龄。扣 1 分是因为评分模型对"超长口令之外的更短口令"做了保守提示，但 12 位已属实践中的强标准。

**阶段九：混合模式 RSA-4096（9/10）。** 验证非对称部分：采用 RSA-OAEP 配 SHA-512（优于老旧 PKCS#1 v1.5，抗选择密文攻击），且私钥永不以明文形式存储（PEM + 主口令加密）。扣 1 分源于评分对"量子计算远期风险"的提示——RSA-4096 在量子前安全，但理论上未来容错量子计算机可破解，故在"量子前"语境下仍给 9 分而非满分。

## 14. 性能基准数据

基于本地实测（Python 3.6.5，Argon2id 默认 256 MB）：

- **密钥派生速率**：约 3.17 次/秒（单次 ~315 ms）。
- **AES-256-GCM 对称加解密**：对常规文本与文件块为微秒级，瓶颈在 Argon2id 而非 AES。
- **雪崩**：单比特明文改动导致密文平均翻转 49.23%（理想 50%）。
- **打包体积**：安装包 `zhcrypt-setup.exe` 约 15.9 MB；安装后约 47 MB（GUI 27.2 MB + CLI 19.5 MB + 说明）。
- **聊天延迟**：消息经 X3DH 建会话后，单条双棘轮加密为毫秒级；网络往返取决于服务器地理位置。

## 17. 典型使用场景与最佳实践

zhcrypt 的能力横跨"个人隐私"与"协作安全"两类需求。下面给出几种高频场景的推荐做法，帮助你把安全能力真正用起来，而不是仅仅"能用"。

### 17.1 个人私密日记与本地存档

如果你只是想给自己留一段只有自己能看的内容（日记、合同草稿、账号备忘），使用**密码模式**即可，无需任何身份或网络。要点是：口令要足够强，且不要和日常登录口令相同；加密结果是一段 Base64 文本，可以存进任意笔记软件、网盘甚至聊天记录，因为内容本身对已方之外的人毫无意义。若担心忘记口令，请配合下一节的密钥分片思路，对个人主口令也做离线备份（例如写在纸上锁进抽屉）。

### 17.2 向他人安全分享文件

把敏感文件发给别人时，优先用**混合模式**：你持有对方公钥，加密后只有对方私钥能解开。如果双方尚未交换公钥，最轻量的办法是用 GUI 的"临时口令"功能——系统生成一组随机中文词作为一次性口令，把"密文"通过任意渠道发送、把"口令"通过**另一个**渠道（例如口头、另一条 IM）告知对方。由于口令只显示一次且不在网络上留存，即使密文被截获也无从解密。注意临时口令适合低频次分享，长期协作仍建议走正式的公钥/身份体系。

### 17.3 团队或好友间的安全通信

需要持续对话时，使用内置的**安全聊天**。首次与某人通信会触发 X3DH 握手，此后每条消息都走双棘轮、具备前向安全。强烈建议在频道建立后，双方各自执行 `chat-safety <对方>` 比对安全识别码——这是人因层面的最后一道防线，能发现"是否有中间人替换了公钥"。识别码一致后在心里默认可信，之后即便服务器被攻破，历史与未来消息仍因 PFS 而安全。

### 17.4 密钥与分片托管策略

私钥丢失等于永久失去解密能力，因此务必使用 Shamir 分片备份（`backup` 生成 5 份、任意 3 份可恢复）。托管建议遵循"地理与介质分散"原则：例如两份存不同云盘、一份存加密 U 盘、一份打印纸质、一份交可信第三人。这样单一灾难（某云盘封号、U 盘损坏、房屋失火）都不会同时损失 3 份。切勿把 5 份全存同一处，那和存整把私钥没有区别。

### 17.5 跨设备迁移

在换新电脑时，不要只拷贝程序，务必同时迁移身份私钥。最稳妥的做法是在旧设备执行 `backup` 拿到分片，在新设备安装好 zhcrypt 后执行 `restore` 重建身份，再删除临时分片文件；或直接把旧设备的密钥存储目录（含加密 PEM）整体复制到新设备，用同一主口令解锁。无论哪种方式，迁移过程都不要在明文状态下把私钥落盘过久。

## 18. 密码学原语深入解析

本节解释 zhcrypt 为什么选这些算法，以及它们各自堵住了哪类攻击。理解"为什么"，比记住"是什么"更能帮你在真实场景做对取舍。

### 18.1 为什么选择 Argon2id

口令的本质问题是"人类记不住高熵随机串"，所以口令空间小、易被暴力枚举。Argon2id 是 2015 年密码哈希竞赛（PHC）的胜出者，也是 RFC 9106 推荐的标配。它的核心思想是**内存硬化**：派生密钥时必须占用大量 RAM（默认 256 MB），且计算无法被有效"节约"。这让攻击者即便拥有 GPU 集群或定制 ASIC，也因内存带宽瓶颈而无法大规模并行——实测普通 CPU 每秒仅约 3 次派生，GPU 每日尝试量也仅亿级，对强口令毫无意义。相比古老的 PBKDF2 或 bcrypt，Argon2id 对现代硬件攻击的抵抗力代差明显。

### 18.2 为什么选择 AES-256-GCM

对称加密负责"快且安全地加密大量数据"。AES-256 提供足够大的密钥空间，抗量子计算前的暴力破解；GCM 是 AEAD（带认证的加密）模式，意味着它**同时保证机密性与完整性**——任何对密文的篡改（哪怕翻转一个比特）都会让认证标签校验失败，解密直接报错，绝不会输出"看似正确但被动过手脚"的明文。这堵住了"篡改攻击"与"填充预言"类漏洞。相比 CBC 这类仅提供机密性的模式，GCM 省去了额外做 HMAC 的步骤，且性能更好。

### 18.3 为什么选择 RSA-4096-OAEP

混合模式中，RSA 负责"把对称密钥安全地交给对方"。4096 位提供远超当前计算能力的密钥空间；OAEP 是优于老式 PKCS#1 v1.5 的填充方案，能抵御选择密文攻击（CCA），并配合 SHA-512 哈希增强健壮性。尽管椭圆曲线密钥更短更高效，RSA-4096 的优势在于生态成熟、互操作性好、且对"量子前"场景已足够，配合下面的棘轮机制还能获得前向安全。

### 18.4 Ed25519 与 X25519 的角色

Ed25519 是签名算法，用于**证明身份**——在签名模式下，接收方可用发送方公钥确认消息确实出自对方且未被改。X25519 是密钥交换算法，用于**协商共享秘密**——双棘轮每次 DH 步进都靠它。两者都基于 Curve25519，计算快、实现简洁、对侧信道较鲁棒，是 Signal 等隐私通讯软件的标配。它们与 RSA 形成互补：RSA 做"初始公钥加密"，Ed/X25519 做"会话内的持续密钥演进"。

### 18.5 HKDF 与双棘轮

HKDF（基于 HMAC 的密钥派生函数）把原始的 Diffie-Hellman 共享秘密"提炼"成均匀、独立的密钥。双棘轮正是用 `KDF_CK`（从链密钥派生消息密钥）和 `KDF_RK`（用 DH 输出更新根密钥）两个 KDF 实现"每次发消息密钥都不同、且一旦泄露不影响前后"。这正是前向安全（PFS）的来源，也是 zhcrypt 聊天优于"一次性 RSA 加密"的根本原因。

## 19. 密钥生命周期与安全运维

密钥不是生成后就一成不变，科学的生命周期管理能显著降低长期风险：

- **创建**：首次 `init` 生成三套密钥（RSA/Ed25519/X25519）。务必为私钥设强主口令，因为私钥以该口令加密存储。
- **使用**：日常加密/聊天时，私钥仅在内存解密、用后即清（`_clear_bytes` 清零），不长期驻留明文。
- **轮换**：长期身份可定期 `delete` 旧身份、`init` 新身份重新分发公钥；聊天会话本身每 30 天过期强制重新协商，天然实现会话级轮换。
- **销毁**：`delete <identity>` 删除本地密钥材料；服务器侧大文件下载即焚，聊天密文不落盘。
- **备份**：如前所述用 Shamir 分片，分散托管。运维铁律——任何服务端行为变更必须改生产副本（`/opt/zhprekey/chat_server.py`）并重启 `zhchat-ws.service`，本地副本改动不生效。

## 21. 故障排查

- **`script not found` / 打包报找不到 gui.py**：多因 PyInstaller spec 中脚本用了相对路径却不在项目根执行。改为绝对路径（如 `C:\Users\20579\zhcrypt\gui.py`）即可。
- **解密报"密码错误或数据已被篡改"**：先确认口令完全一致（注意中文输入法全角/半角、首尾空格）；再确认密文完整未被截断。GCM 不会"差一点"，失败即代表口令不对或数据损坏。
- **聊天连不上服务器**：检查 `set-server` 地址是否正确、`upload-prekey` 是否已执行；用 `wss://` 时确认服务器证书有效（或先用 `cert-pin` 固定指纹）。本地调试可用 `ws://`。
- **大文件上传中途断开**：确认服务端 `max_size` 已调大到 100 MB 且服务已重启；客户端 websocket-client 本身无此限制。
- **CLI `--help` 中文乱码**：终端编码问题，非程序错误，实际功能正常；建议 Windows Terminal 或 `chcp 65001`。
- **程序启动报缺模块**：源码运行请确保 `pip install -r requirements.txt` 且 `lib/` 依赖目录未被删除。

## 23. 常见问题（FAQ）

**Q1：CLI 和 GUI 加密的结果能互通吗？**
能。二者共用 `core.py`，数据包格式一致。GUI 加密的密文粘贴进 CLI 同样可解密。

**Q2：忘记密码怎么办？**
密码模式无法找回——没有"找回密码"后端，这是设计使然（服务器不持有密钥）。请用密钥分片备份（`backup`/`restore`）保护身份私钥；但文本口令本身无备份。

**Q3：服务器能看到我的消息内容吗？**
不能。聊天内容经 X3DH + 双棘轮端到端加密；文件内容全程 AES-GCM 且密钥不经服务器。服务器只是密文中转站。

**Q4：大文件发送后对方没下载，文件会一直留服务器吗？**
不会。有 30 分钟兜底清理；且一旦下载成功立即删除（`os.remove`）。

**Q5：中文口令真的安全吗？**
非常安全。中文字符集约 5000，单字贡献 ~12 bits 熵，一句短语轻松超过 80 bits（"极强"档），远超纯英文数字口令。

**Q6：为什么 --help 在 Windows 终端中文乱码？**
PowerShell/CMD 默认 GBK 编码，而程序输出 UTF-8。属显示问题，不影响功能；实际加密/解密的中文内容正常。可在 Windows Terminal 或设置 `chcp 65001` 解决。

**Q7：Argon2id 256 MB 太慢，能调小吗？**
能，用 `set-params` 调低 `memory_cost`。但这会削弱抗暴力破解能力，仅建议在低配设备上权衡。

**Q8：lib/ 目录可以删吗？**
不可以。`lib/` 是运行时依赖（cryptography/argon2/websocket 等），删除后程序无法运行。可清理的是 `build/`、`dist/`、`dist_installer/`、`.pytest_cache/`、`__pycache__/` 等可重建产物。

**Q9：GUI 和 CLI 能同时使用同一个身份吗？**
可以。二者读写同一套本地密钥库（KeyStore），身份信息完全共享。例如你可以在 GUI 里 `init` 创建身份、导入对方公钥，然后到 CLI 用 `chat-send` 发消息，反之亦然。注意同一身份的私钥主口令需一致才能解锁。

**Q10：消息发错人了能撤回吗？**
由于采用端到端加密、服务器不持有明文，系统没有中心化的"撤回"能力。你可以用 `chat-delete` 删除自己设备上的会话记录，但对方设备上已收到的内容仍在。因此请务必在发送前通过安全识别码确认对端身份——"发前确认"比"发后撤回"更可靠。

**Q11：支持哪些操作系统？**
zhcrypt 基于 Python 3.6+ 实现，Windows、Linux、macOS 均可运行；Windows 平台已提供图形化安装包（zhcrypt-setup.exe），其他系统推荐源码运行（见第 4 章）。移动端（iOS/Android）目前不在支持范围。

**Q12：加密后的密文能直接当文件保存吗？**
可以。密码模式与混合模式产出的文本密文是 Base64 字符串，可存进任意文本文件或笔记；文件加密模式则产出 `.zhc` 等二进制密文文件，二者均可用 GUI 的对应标签页或 CLI 的 `decrypt` / `decrypt-file` 还原。无论哪种形式，密文本身不含口令或私钥，泄露也无妨，真正要保护好的是你的主口令与私钥分片。

## 24. 术语表与阅读指引

为方便不同背景的读者，本节先给出核心术语的中文释义，再按角色给出阅读建议。

### 24.1 术语表

- **Argon2id**：2015 年密码哈希竞赛胜出算法，RFC 9106 推荐。通过"内存硬化"让口令派生难以被显卡并行暴力破解。
- **AEAD（认证加密）**：一种同时保证机密性与完整性的加密模式，代表性的是 AES-GCM。任何密文篡改都会被检测。
- **AES-256-GCM**：高级加密标准、256 位密钥、GCM 模式的认证加密，负责大量数据的快速加解密。
- **RSA-4096-OAEP**：4096 位 RSA 非对称加密，采用 OAEP 填充（优于旧式 PKCS#1 v1.5），用于把对称密钥安全交给对方。
- **Ed25519**：基于 Curve25519 的签名算法，用于证明消息发送者身份、防伪造。
- **X25519**：基于 Curve25519 的密钥交换算法，用于协商共享秘密，是双棘轮每次步进的基础。
- **X3DH（扩展三重迪菲-赫尔曼）**：Signal 风格握手协议，用多轮 DH 协商出初始会话根密钥。
- **Double Ratchet（双棘轮）**：在 X3DH 基础上，每条消息推进链密钥、定期轮换根密钥，提供前向安全。
- **PFS（前向安全）**：即便长期私钥日后泄露，历史通信记录仍无法被解密的性质。
- **HKDF**：基于 HMAC 的密钥派生函数，把共享秘密"提炼"成均匀独立的密钥。
- **Shamir 秘密共享**：将秘密分割为若干份、满足阈值即可恢复的密码学方案，zhcrypt 用 5 份任取 3 份。
- **Safety Number（安全识别码）**：由双方公钥派生的可比对数字，用于确认通信信道未被中间人篡改。
- **Prekey（预密钥）**：提前生成并上传服务器的一次性密钥，供他人发起 X3DH 会话。
- **Magic（魔数）**：数据包头固定标记 ZHCR，用于快速识别 zhcrypt 格式。
- **Nonce / Salt**：分别为对称加密的随机初始化向量与口令派生的随机盐，确保相同输入每次产出不同密文。
- **DEK（数据加密密钥）**：混合模式中随机生成的对称密钥，用对方公钥加密后随密文发送。

### 24.2 分角色阅读指引

- **普通用户**：从"第 5 章 快速开始"入手，重点看 GUI 六标签页（第 8 章）与 FAQ（第 23 章）；加密文件用混合模式或临时口令；牢记"强口令 + 比对安全识别码"两条铁律。
- **开发者 / 安全研究员**：直接读"第 6 章 加密原理"与"第 18 章 原语解析"，结合 core.py、ratchet.py 源码；如需做红队测试，参考 docs/ 中的 zhcrypt_redteam_report.md。
