## 二、加密强度量化评估

| 组件 | 参数 | 安全强度 | 备注 |
|---|---|---|---|
| 会话密钥（X3DH） | X25519 + HKDF-SHA256 | ~128-bit | 量子前安全；Q-day 后需 PQC 迁移 |
| 混合加密 DEK | AES-256-GCM | 256-bit（量子 Grover 下 128-bit） | |
| RSA 密钥 | RSA-4096 OAEP-SHA512 | ~140-bit | NIST 建议 2030 年前迁移 PQC；当前无实际攻击 |
| 签名 | Ed25519 | 128-bit | |
| **口令派生（安全下限）** | Argon2id m=256MB t=4 p=4 | 取决于口令熵 | **整个系统的安全下限 = 用户密码强度** |

Argon2id 参数对照 RFC 9106 基线：RFC 推荐 `m=64MiB/t=3/p=4`（最低）或 `m=2GiB/t=1/p=4`（高性能）；本实现 **256MB/t=4 更保守**，单次派生本机实测 ~0.9s，离线暴力破解成本高（256MB 内存约束使单卡并发仅数个实例）。弱口令（<30bit 熵）仍分钟级可破——与完整手册量化一致，必须依赖强度检测与用户选择。

## 四、问题清单（按严重度）

### 4.1 【中】Windows 上私钥文件权限未真正收紧
`config.py _load_device_key` 与 `keys.py` 使用 `os.chmod(0o600)`——**Windows 上该调用基本无效**（仅影响只读位，不限制访问）。`~/.zhcrypt/` 目录继承默认 ACL，同机其他用户/进程可读密钥包裹文件与 device.key。
- 缓解：包裹文件经 Argon2id+AES-GCM 加密，离线破解仍需密码；且 device.key 泄露仅影响本地 token
- **处置记录**：曾尝试在 `ensure_config_dir` 内自动执行 `icacls /inheritance:r /grant:r %USERNAME%:F`，但在多账户/代理执行环境下 `USERNAME` 可能非真实用户，会误伤他人目录 ACL（实测导致 ~/.zhcrypt 不可访问、测试全挂）——**已回滚**。
- 正确做法（列入 3.2）：由安装器/首启向导以**实际交互用户**身份执行一次：
  `icacls "%USERPROFILE%\.zhcrypt" /inheritance:r /grant:r "%USERNAME%:F" /T`
  或在文档中给出该命令由用户手动执行。

### 4.2 【中】SPK（签名预密钥）无定期轮换
`ensure_own_prekey` 仅在 OTP 剩余 <10 时重传 bundle（每次重传会替换 SPK），若 OTP 充足则 SPK 可长期不变。X3DH 规范建议 SPK 按天/周轮换，长期固定 SPK 扩大单点风险。
- 建议：bundle 重传策略中加入 SPK 最大寿命（如 7 天），与服务器 `PREKEY_EXPIRE_DAYS` 对齐

### 4.3 【中】Double Ratchet 不轮转（协议设计局限）
已在上轮审查记录：`_dh_ratchet_step` 在当前消息流下永不触发，会话密钥无周期性 DH 刷新。前向安全仍成立（链密钥单向推进，泄露当前链密钥无法反推历史消息密钥），但无 post-compromise security。协议改造需与旧客户端不兼容，列入 3.2。

### 4.4 【低】密码无 Unicode 规范化
`password.encode("utf-8")` 直接输入 Argon2id，未做 NFC 规范化。组合字符（如 `é` 可为 `U+00E9` 或 `e+U+0301`）在不同输入法/平台下产生不同密钥 → 解密失败。中文密码无此问题，但建议输入侧 NFC normalize 或文档注明。

### 4.5 【低】消息签名绑定服务器时间戳
签名体 `{sender}{server_ts}{text}` 中时间戳来自服务器（`msg["timestamp"]=server_ts`）。被攻陷服务器可篡改时间戳导致验签失败（DoS 面），但无法伪造签名。缓解：本地记录最近服务器时间戳漂移检测（可选）。

### 4.6 【低】流式文件加密：文件名明文
密文头含原始文件名（恢复输出名所需）。泄露文件元数据。建议：可选"文件名加密"选项（密文包内加盐文件名，输出时提示）。

### 4.7 【低】可否认加密：明文长度泄露
包头以 4 字节字段暴露 real/duress 两段密文各自长度，攻击者可观测真实消息长度模式，削弱可否认性。缓解：固定填充至对齐长度（代价是体积）。

### 4.8 【建议】GCM 随机 nonce → 计数器 nonce
消息量 >2^32 时随机 nonce 碰撞风险显现。当前场景不可达；若未来做群聊/广播可改计数器派生（Signal 式）。

### 4.9 【建议】config 中 argon2id 参数可被本地放大导致 OOM
`_get_argon2_params()` 信任 config.json 的 memory_cost（如被误配为 16GiB → 解密时 OOM）。本地攻击者已有更高权限，低危；建议派生时钳制上限（如 ≤2GiB）。

### 4.10 【已排除】消息重排攻击
会话消息 AAD 仅含 session_id 而不含消息号——已分析：消息密钥按链号 KDF 派生，交换两条密文会使解密失败（密钥错位），不存在可用的重排攻击面。✓

## 五、总体结论

| 维度 | 评级 | 说明 |
|---|---|---|
| 原语正确性 | **A** | 22/22 KAT 与官方向量逐位一致 |
| 参数选择 | **A-** | Argon2id 优于 RFC 9106 基线；RSA-4096/OAEP-SHA512 保守正确 |
| 实现缺陷 | **B+** | 无利用性缺陷；3 项中危（Windows 权限/SPK 轮换/ratchet 局限）均非可利用漏洞 |
| 抗篡改/重放/重排 | **A** | GCM 认证 + AAD 绑定 + 消息去重 + 链号派生，实测通过 |
| 侧信道 | **A** | 常量时间比较、CSPRNG（secrets）、无日志泄露密钥 |
| 安全下限 | **由用户密码决定** | Argon2id 防护到位，弱密码仍可离线破解（手册已量化 ≥80bit 建议） |

**判定：加密段无致命或高危缺陷，密码学方案与实现处于专业水平，与官方标准向量完全一致。** 三项中危问题（Windows 私钥 ACL、SPK 轮换策略、ratchet 轮转）建议在 3.2 版本处理；其余为可选项。系统整体安全强度取决于用户密码质量与私钥本机防护，建议：≥80bit 熵密码 + 开启 Shamir 备份 + Windows ACL 加固。
