## 二、实测打穿的漏洞

### 🔴 #8 Auth Token 明文存储（高危，已实测确认）

- **证据**：读取本机 `~/.zhcrypt/config.json`，`prekey_server.auth_token` 以**明文**存在（长度 32，非空）。本报告不回显该值。
- **攻击者路径**：获取该文件（机器丢失/被盗、配置文件同步到云盘或备份、任意可读权限）即可提取 token，直接冒充该用户连接服务器、收发其消息。
- **影响**：身份冒用、消息读取、会话接管。CWE-312（明文存储敏感信息）。
- **现状**：`config.py` 直接用 `json.dump` 写出整个配置，token 字段无任何加密。

### 🔴 #3 / #4 + #18 + #5残余 组合：无 TLS → 中间人可透明解密全部聊天（严重，代码确证）

这是当前最危险的链路。代码证据：

- `chat_client.py:207`：`sslopt={} if "wss://" not in self._ws_url else {}` —— 无论 `wss://` 与否，`sslopt` 都是空 dict。即使用 `wss://`，**客户端也不校验证书**（#18 实锤：任意 CA 签发的证书都被接受）。
- 你的客户端配置 `prekey_server.url` 指向生产服务器，WS 会被推导为 `wss://`，但 `sslopt` 为空 → 传输层可被中间人劫持。
- `chat_client.py:240-287`（`_initiate_session` 的 X3DH 握手）：
  - 首次接触时 `local_pub` 为空，`verify_key = bundle_signing_pub`（来自服务器返回的 prekey bundle **自身**）；
  - `ed25519_verify(bundle_signing_pub, spk_pub_pem, spk_sig)` —— 攻击者用**自己的签名私钥**对**自己的 signed prekey** 签名，校验必过；
  - 首次接触分支（`:285-287`）将攻击者的签名公钥**固定为 TOFU 信任锚**；
  - 握手"成功"，后续 Double Ratchet 会话密钥由攻击者的密钥参与 → **攻击者能解密全部后续消息**。
- `#5` 残余：带外 safety number 确认未在 CLI/GUI 交互层落地 → 用户**没有任何手段察觉**公钥被替换。

- **攻击者路径**：处于能碰你网络的位置（公共 WiFi、恶意/被控 ISP、骨干旁路）→ 对 prekey 下载 / WS 做 MITM → 替换 prekey bundle 为攻击者密钥 → 受害者无感知完成与攻击者的握手 → 全部"端到端加密"消息被攻击者解密。
- **影响**：**端到端加密被彻底绕过**，通信内容完全暴露。严重级。
- **关键提醒**：即便先把 #3/#4 补上（上 `wss` + 证书），只要 #18（证书固定）和 #5 残余（带外确认）没一起修，持合法 CA 证书的 MITM 仍能劫持——三者必须联动修复。

## 三、低危（可后续安排）

- 🟡 **#16** HKDF 使用固定 salt：理论上削弱 KDF 抗生日悖论强度，当前场景实际影响低；修复需协议兼容（salt 随包传输）。
- 🟡 **#17** Shamir 秘密共享使用 secp256k1 质数：非标准安全质数，但 secp256k1 本身是大安全质数，实际风险低；迁移需兼容旧份额。

## 四、总体评级

- **已修防线**：扎实。发送者认证、路径穿越、权限模型、限流、TOFU 换钥检测均有效。
- **致命短板在传输层与凭证存储**：#8（明文 token）+ #3/#4/#18/#5残余（MITM 解密）形成组合，意味着一个能接触你网络或你配置文件的人可以完全掌控通信。
- **给朋友用之前**：#3/#4/#18/#5残余 + #8 必须修复，否则"端到端加密"是虚假的安全感。
